# Hebbian plasticity on the cooperative transport task

Material for a talk on the evolved-plasticity controller: what the genome contains, how the variants compare
on the standard (fixed-attachment) transport task, and what happens when the cable attachment points are
randomized so a fixed agent identity stops being informative.

Everything here is regenerated by two scripts in this folder, so nothing is hand-curated:

```bash
bash presentation/make_videos.sh    # the clips in videos/   (one GPU, sequential, ~20 min per clip)
bash presentation/run_eval.sh       # the numbers in results/comparison.csv (headless, 128 envs)
```

## The task

`Isaac-flycrane-payload-decentralized-hovering-v0`: three quadrotors suspend a basket on three cables and must
carry it to a commanded pose (position and yaw), which is resampled during the episode. Control is
decentralized: each drone outputs an acceleration plus body rates (5 numbers) and observes only its own
45-dimensional partial view of the scene. Episodes last 20 s; a pose counts as achieved inside 0.3 m.

## The method

A conventional policy stores what it learned in fixed weights. Here the weights are not stored at all. Every
synapse updates online, during the episode, by a Hebbian rule whose per-synapse coefficients are what
evolution searches:

```
Δw = lr · (A·pre + B·post + C·pre·post + D)        # optionally anchored toward w_init
```

`pre` and `post` are the activations either side of the synapse. Evolution (OpenAI-ES or PGPE) searches the
coefficient vectors, not the weights. The three drones are homogeneous and share one genome. Each parallel
Isaac environment evaluates one candidate, so the whole population is scored every generation on the GPU.

The network is tiny: 45 inputs → 4 hidden → 5 actions, no biases, so **200 plastic synapses per drone**.

### Genome variants

| variant | evolved blocks | genome | what it adds |
|---|---|---|---|
| ABC | A, B, C | 600 | correlation-driven plasticity only, weights start random |
| **ABCD** | A, B, C, D | 800 | adds the constant drive term D |
| **ABC+W** | A, B, C, W₀ | 800 | drops D, instead evolves the **initial weights** each episode starts from |
| **ABCD+W** | A, B, C, D, W₀ | 1000 | full rule plus evolved initial weights |

The three bold rows are what the code can actually build and what we have trained. A pure **ABC** genome is
**not reachable** in the current implementation: `hebbian_core.py` sets `use_d = (not evolve_init_weights) or
keep_d`, so the D block is forced on whenever the initial weights are not evolved. See "What is missing".

## Part 1 — fixed attachment: what the genome has to encode

All three clips are the same task, same seed, same camera; only the genome layout differs.

| clip | variant | genome | best training fitness |
|---|---|---|---|
| `videos/1a_fixed_ABCD.mp4` | ABCD | 800 | 95.5 |
| `videos/1b_fixed_ABCW.mp4` | ABC+W | 800 | 184.7 |
| `videos/1c_fixed_ABCDW.mp4` | ABCD+W | 1000 | 190.7 |
| `videos/1d_fixed_mappo.mp4` | MAPPO baseline (the paper's released policy) | ~0.83 M weights per agent | n/a |

The story in one line: **the evolved initial weights, not the D term, are what make this work.** Going from
ABCD (random initial weights, 95.5) to ABC+W (evolved initial weights, 184.7) nearly doubles fitness; adding D
back on top (ABCD+W, 190.7) is a small further gain. Plasticity alone cannot bootstrap a useful controller
inside one episode — it needs a sensible starting point to adapt *from*.

For scale: the MAPPO baseline carries about 0.83 M weights per agent; the Hebbian genome is 1000 numbers
shared by all three drones, roughly 2500× smaller.

## Part 2 — randomized attachment: when agent identity stops being informative

`Isaac-flycrane-payload-decentralized-hovering-rand-v0` with `--attachment_per_env 1`. Each environment gets
its own cable geometry: the three anchor points slide along the basket rim (arcs covering all four walls,
kept non-crossing), and the basket mass is randomized 0.9–1.9 kg.
`videos/0_context_randomized_attachment.{png,mp4}` shows the anchor spread.

This breaks an assumption the MAPPO baseline was trained under. In the fixed task each agent has a one-hot
identity that implicitly tells it which corner of the load it is holding, so "I am falcon2" is enough to know
the geometry. Once the anchors move, that identity carries no geometric information, and the observation slot
that held the one-hot now carries a target-wall directive the pretrained policy never saw.

| clip | controller | trained on |
|---|---|---|
| `videos/2a_rand_mappo.mp4` | MAPPO baseline | fixed attachment (agent id informative) |
| `videos/2b_rand_hebbian.mp4` | Hebbian ABCD+W | randomized attachment (fitness 167.4) |
| `videos/2c_rand_hebbian_fixedtrained.mp4` | Hebbian ABCD+W | fixed attachment, dropped in cold (fitness 190.7) |

### Numbers

`results/comparison.csv`, all controllers under one protocol (128 environments, shared seed, identical metric
definitions). Filled in by `run_eval.sh`.

An earlier run of the same comparison (2026-07-07, best-of-that-date checkpoints) gave the shape of the
result:

| | MAPPO baseline | Hebbian |
|---|---|---|
| fixed attachment, episode return | 232 | 157 |
| fixed attachment, success rate | 95 % | 23 % |
| randomized attachment, episode return | 50 | 107 |
| randomized attachment, success rate | 22 % | 4–6 % |

Read it by metric, because the ranking flips. By **return** the plastic controller degrades gracefully: MAPPO
loses about 78 % of its return when the attachment is randomized, the Hebbian controller about 36 %, and ends
up roughly twice as high. By **success rate** at the strict 0.3 m bar MAPPO still wins even when perturbed,
because when it does not lose the load it tracks tightly. Randomized anchors shift the load's centre of mass,
which produces a real steady-state offset that a 200-weight network cannot trim out.

## What is missing

Three gaps, in the order they would matter for the talk.

1. **A pure ABC run does not exist and cannot currently be produced.** The D block is forced on whenever the
   initial weights are not evolved, so the smallest genome the code can build is ABCD (800). Getting a true
   three-block ABC point needs a one-line change in `hebbian_core.py` (let `use_d` be false when
   `evolve_init_weights` is false) plus one evolution run, about 8 h on the RTX 4090. Until then the honest
   ablation axis is **ABCD → ABC+W → ABCD+W**, which is arguably the more interesting one anyway: it isolates
   the evolved initial weights rather than the bias term.

2. **The ABCD baseline is not hyper-parameter matched to the others.** The 95.5 run used PGPE, population 512,
   plasticity applied every step, learning rate 0.1. The two +W runs used OpenAI-ES, population 512–1024, and
   update intervals of 50–100 steps. So part of the ABCD → ABC+W jump is optimizer and update-interval, not
   only the genome. A matched ABCD run under the ABCD+W settings would cost one more 8 h run and would make
   the ablation clean.

3. **There is no MAPPO trained on the randomized-attachment task.** The MAPPO clips use the paper's released
   `3_mav.pt`, trained on fixed attachment. That is the right demonstration of "a fixed agent identity stops
   being informative", but it is a transfer result, not a like-for-like comparison. If the claim you want is
   "MARL cannot learn this task at all when the attachment is random", that run has not been done. Our own
   MAPPO logs contain only smoke tests.

Also worth knowing: the randomized-attachment Hebbian checkpoint was trained with domain randomization but
that helped only marginally (return 100 → 107, success slightly worse), and the gap between its training
fitness (167) and evaluation return (107) is selection bias from the noisy per-environment randomization.
